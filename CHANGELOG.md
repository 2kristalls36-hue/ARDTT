## стек 1.0.53 — overlay /etc 0644

- Образ **1.0.52** сразу уходил в crash-loop (`Restarting`): `COPY --chmod=644` в `FROM scratch AS overlay` выставил каталогам `/etc` и `/opt/ardtt/telemetry` режим 0644 (BuildKit применяет chmod к созданным родителям). Overlayfs применил это к Debian `/etc` — без +x не читаются `passwd`, `resolv.conf`, `/etc/ssl`. `docker exec` для `ready.sh` отвечал «Container is restarting»; установщик откатывал предыдущую версию. В overlay `--chmod` только 0755; шаблон dnsmasq и `app.py` копируются без `--chmod` в `/opt/ardtt` (слой больше не содержит заголовок каталога `/etc`). `wait_readiness` выходит после трёх `Restarting`; в ошибке — `docker inspect` и хвост `docker logs`.
- **Attach built packages.** Гонка с Android build брала артефакт предыдущего `versionName` (искали `ardtt-0.5.264-*`, скачали 0 файлов с run 0.5.263) и падала до прикрепления стека. Если APK этой версии уже на теге — пропускаем заливку APK и всё равно крепим пакеты сервера. Engine/Compose с теми же именами (29.7.2 / 2.32.4) на теге не блокируют новый стек: совпавший digest пропускается, на релиз уходят только архив/индекс/слои 1.0.53.

## стек 1.0.52 — частичный деплой

- **Покомпонентный релиз.** Рядом с монолитным `ardtt-server-<ver>-linux-<arch>.tar.gz` на каждую arch публикуются `*.index.json` (+ `.sha256`, формат `ardtt-server-index-v1`: все компоненты с SHA-256 и размером), `*-hostfiles.tar.gz` (`install.sh`, `fetch-and-install.sh`, `install-lib/`, `scripts/`, Compose-файлы, `manifest.json`, `images/layout.json` + `config.json`, `third-party.lock.json`, `DEPLOY_VERSION`; ≈100 КБ), по одному gzip на слой образа `*-layer-NN-<16hex>.tar.gz` (адресация по diff ID слоя), `ardtt-docker-engine-29.7.2-linux-<arch>.tgz` (85,7 МБ amd64 / 77,3 МБ arm64) и `ardtt-docker-compose-2.32.4-linux-<arch>` (64,7 МБ amd64 / 62,9 МБ arm64) — оба побайтно те же, что `vendor/docker.tgz` и `bin/docker-compose` внутри архива. `SHA256SUMS-server.txt` перечисляет всё это.
- **VPS качает только недостающее.** Полный архив 1.0.51 на релизе `v0.5.263` — 182,3 МБ amd64 / 169,8 МБ arm64, из них Engine 85,7 МБ и Compose 64,7 МБ отдельными ассетами; gzip-слои образа — 78,3 МБ (23 слоя, из которых два базовых, Debian и apt, ≈57 МБ и меняются только при бампе базы), host-файлы 56 КБ. Обновление на VPS с уже работающим Docker тянет не больше слоёв (≤78 МБ при пустом кэше без загруженного образа), а при тёплом кэше — только изменившиеся слои (обычно маленькие слои со скриптами и provision). Проверено на двух чистых VPS (Debian 13, Ubuntu 26.04): повторное обновление — 3 запроса, индекс 5 КБ + host-файлы 56 КБ, ноль слоёв. Кэш `/opt/ardtt/cache/layers/<diffId>.tar.gz` перед загрузкой засевается из уже загруженного образа через `docker save` (`scripts/layer-cache.py`) и после успешной установки прунится до слоёв текущего образа (≈78 МБ на диске). `ARDTT_LAYER_CACHE=0` отключает постоянный кэш.
- **`fetch-and-install.sh` на VPS.** Протокол с телефоном и переменные не изменились (`ARDTT_PROGRESS|` / `ARDTT_WARN|` / `ARDTT_ERROR|` / `ARDTT_DONE|`). Релиз выбирается через GitHub API (`releases?per_page=40`) по **наибольшей** версии стека среди релизов-нечерновиков, а не по первому подходящему активу; `ARDTT_DEPLOY_VERSION` закрепляет версию, `ARDTT_GITHUB_TOKEN` снимает анонимный лимит API. Если API недоступен или отдал 403/429 — `ARDTT_WARN|GitHub API недоступен …` и продолжение по `SHA256SUMS-server.txt` последнего релиза через `releases/latest/download/…` (без API). `ARDTT_FETCH_MODE=auto` (индекс, если он есть) | `partial` (иначе `INDEX_MISSING`) | `full`. Engine качается только если на хосте вообще нет `docker` CLI; Compose — только если нет ни плагина `docker compose`, ни `docker-compose`, а `/opt/ardtt/bin/docker-compose` отсутствует или не совпадает с закреплённой SHA-256.
- **Доверие и надёжность загрузки.** Корень доверия частичной установки — внешняя SHA-256 индекса (`digest` актива, иначе `SHA256SUMS-server.txt`, иначе сосед `.sha256`); дальше по индексу сверяется каждый host-файл, каждый слой (gzip-SHA-256 **и** diff ID), Engine и Compose. Загрузки возобновляемые (`curl -C -`, `.partial` в `incoming/`), с обрывом при скорости <1 КБ/с дольше 90 с и повторами; битый файл при `SHA256_MISMATCH` удаляется, чтобы повтор скачал заново. Один запуск на каталог установки — `/opt/ardtt/fetch.lock`. Новые коды: `BUSY`, `INDEX_MISSING`, `BAD_FETCH_MODE`, `SHA256SUM_MISSING`; `GITHUB_UNREACHABLE` теперь означает и провал fallback'а по `SHA256SUMS-server.txt`.
- **`install.sh`: индексный режим.** С `ARDTT_PACKAGE_INDEX` / `ARDTT_PACKAGE_INDEX_SHA256` внешняя сумма архива не проверяется (архива нет): сверяются SHA-256 индекса и все подготовленные файлы — **до** остановки живого стека. После `docker load` gzip-слои не удаляются, а переезжают в `/opt/ardtt/cache/layers`; это делает и монолитный путь, поэтому первое частичное обновление после полной установки уже переиспользует слои. `/opt/ardtt/bin/docker-compose` (наша копия) обновляется, если пакет несёт другую закреплённую сборку; системный плагин не трогается. `images/layout.json` + `images/config.json` остаются в `releases/<ver>/` и `current/`. Uninstall убирает и `cache/`, и `fetch.lock`.
- **Архив снова содержит `fetch-and-install.sh`.** Раньше pack-скрипт не включал его в tar, поэтому `/opt/ardtt/current/fetch-and-install.sh` не появлялся и телефон каждый раз заливал bootstrap из APK. Теперь скрипт есть и в архиве, и в host-файлах: после первой установки 1.0.52 `DeployEngine` запускает копию с VPS. Путь обновления отвязан от версии APK — старые bootstrap'ы (≤0.5.263) продолжают работать по монолитному архиву, который по-прежнему публикуется.
- **Стабильные слои образа.** `server/Dockerfile` закрепляет базовые образы по digest (`golang:1.22-alpine`, `golang:1.25-bookworm`, `debian:bookworm-slim`; digest'ы в `server/third-party.lock.json` → `baseImages.digests`, сверяет `scripts/check-deploy-bundle.sh`), ставит режимы через `COPY --chmod` (хвостового `RUN chmod`, который переписывал все бинарники одним слоем, больше нет), даёт по слою на Go-бинарник и сводит entrypoint'ы/helpers/шаблоны в один overlay-слой (`FROM scratch AS overlay`). `scripts/build-server-image.sh` идёт через `docker buildx build --load` с опциональными `ARDTT_BUILD_CACHE_FROM/TO`; workflow пакета передаёт BuildKit-кэш `type=gha` на каждую arch, поэтому неизменившиеся шаги дают побайтно те же слои между сборками.
- **CI и provision.** `scripts/build-server-index.py` собирает индекс и покомпонентные ассеты, `scripts/verify-server-index.sh` проверяет индекс в сборке, `scripts/attach-server-packages-to-release.sh` прикрепляет все новые ассеты и отказывается публиковать индекс с отсутствующими или несовпавшими компонентами (по-прежнему без `--clobber`). Новые тесты: `scripts/test-fetch-partial.sh` (чистый VPS, обновление изменившегося слоя, подменённый актив, недоступный API, полный и legacy fallback против локального фейкового GitHub) и `scripts/test-layer-cache.sh`; `split-docker-save.py` и `assemble-docker-save.py` работают потоково и падают при расхождении diff ID. `/health.latestDeployVersion` берёт наибольшую версию стека по всем релизам-нечерновикам, распознаёт `.tar.gz` и `.index.json` и игнорирует ассеты host-файлов, слоёв, Engine и Compose.
- **Проверка на чистых VPS (Debian 13 и Ubuntu 26.04, 1 vCPU, без Docker).** Найдено и исправлено: (1) `install_bundled_compose` проверял `-x` у `bin/docker-compose`, а безопасная распаковка не сохраняет права — на чистом VPS без Compose-плагина установка 1.0.51 падала с «Нет Docker Compose v2» сразу после подъёма Engine из архива (CI не видел: на runner'ах плагин есть); (2) в минимальном Debian нет `curl` — раньше `CURL_MISSING`, теперь загрузка через python3 urllib (Range-возобновление, повторы), и ключ входа каскада на выход тоже уходит без curl; (3) в обоих образах нет `iptables`, без него Docker не поднимает сети — теперь он ставится автоматически из репозитория дистрибутива до загрузки Engine (см. ниже); (4) старые архивы в `incoming/` после успешной частичной установки удаляются. Прогон: свежая частичная установка (Engine и Compose из релиза, 23 слоя), повторное обновление (3 запроса, ноль слоёв), посев кэша из загруженного образа (`seeded 23 layers`, ноль загрузок), uninstall с purge, каскад вход/выход с handshake и provision выхода через overlay `10.10.0.2`.
- **Изоляция на живом сервере.** Проверено на боевом VPS со сложной конфигурацией (Docker 29.1.3 с чужим контейнером Amnezia, хостовые `wdtt-server`/`dnsmasq`/`wireproxy`, `wg1`/`wdtt0`/`tun-warp`, 526 правил iptables с `FORWARD DROP`, policy-routing, ufw, fail2ban): полный снимок «до», установка с фоновым зондом соседей, снимок «после», uninstall, снимок «после снятия». Установка добавила только свой контейнер, bridge `172.28.20.0/24`, veth и Docker-правила для него (ни одного удалённого правила, nft/sysctl/маршруты/ip rule/systemd/ufw/fail2ban без изменений); соседи (контейнер, пиды, WireGuard-пиры, DNS) не дрогнули; после uninstall состояние идентично исходному. Найден и исправлен баг: Compose ставит переменные окружения выше `.env`, а телефон экспортирует **запрошенные** порты — при занятом `udp/56003` автовыбор писал в `.env` 56004, но compose пытался занять 56003 («failed to bind host port»). Теперь `compose_up_cmd` запускает Compose под `env -i` (только PATH/HOME/`COMPOSE_PROJECT_NAME`/`DOCKER_*`), и `.env` — единственный источник портов и лимитов; неудавшийся первый `compose up` больше не оставляет контейнер в `Created` и сиротскую сеть.
- **Одна кнопка на чистом VPS.** Единственное исключение из «только релиз»: если Docker ставится из пакета, а `iptables` на хосте нет, установщик берёт его из репозитория дистрибутива (`install-lib/hostdeps.sh`: apt/dnf/yum/apk/zypper) — после host-файлов и до загрузки Engine; `ARDTT_INSTALL_IPTABLES=0` запрещает это и даёт `IPTABLES_MISSING` с командой для ручной установки. Preflight приложения лишь отмечает отсутствие iptables (`docker-and-iptables-from-package`), не останавливая деплой. Ошибки `fetch-and-install.sh` теперь с `code=…`, как у `install.sh`, поэтому приложение показывает понятные сводки для `BUSY`, `PACKAGE_RESOLVE`, `SHA256_MISMATCH`, `IPTABLES_MISSING`.
- **Приложение: ожидаемая версия стека.** `DeployStackSource.latestServerVersion` (то, что `DeployVersionCatalog` пинит в `ARDTT_DEPLOY_VERSION`) раньше брал версию первого попавшегося `ardtt-server-*.tar.gz`: при двух стеках на одном релизе карточка требовала обновления до 1.0.52 по `/health`, а деплой ставил 1.0.51. Теперь — максимум по semver, как на VPS и в provision; `.index.json` учитывается, ассеты hostfiles / слоёв / Engine / Compose нет. Код приложения в остальном не менялся — оно по-прежнему только запускает установку/обновление/удаление по SSH и управляет клиентами.

# ARDTT v0.5.263

Клиент **0.5.263** (`versionCode` 281). Серверный стек **1.0.51** (`DEPLOY_VERSION`).

GitHub Release `v0.5.263`: APK, `ardtt-update.json`, `ardtt-server-1.0.51-linux-{amd64,arm64}.tar.gz`.

## 0.5.263 / стек 1.0.51

- **Деплой с VPS, не с телефона.** Каскад: телефон только SSH-триггер. `fetch-and-install.sh` на VPS сам качает `ardtt-server-<ver>-linux-<arch>.tar.gz` с GitHub Releases, сверяет SHA-256 и ставит. Пакет на телефон не тянется и по SFTP не заливается.
- **Диск.** Мягкий пол места (~1600 МБ), gzip-слои образа без второго полного `ardtt.tar` на диске. При `DISK_FULL` — опциональная безопасная очистка (`ARDTT_DISK_CLEANUP=1`) и кнопка «Очистить место и повторить».
- **1 vCPU.** Compose `cpus` / mem clamp по `nproc` хоста (`ARDTT_CPUS` / `ARDTT_MEM_LIMIT` с телефона). Иначе на 1-ядерном VPS `docker compose up` падал с «range of CPUs is from 0.01 to 1.00».
- **Метрики хоста.** В `GET /health` — объект `host` (CPU/RAM cgroup, диск `/data`). В карточке сервера кольца загрузки, опрос ~10 с + pull-to-refresh.
- **Версия обновления.** Ожидаемый стек = max(tip GitHub Releases, `DEPLOY_VERSION` из git/APK). UI показывает обновление, если на VPS старше, чем tip Releases / APK.

Промежуточные стеки в этой линейке: **1.0.47** (fetch на VPS), **1.0.48** (layered/gzip + мягкий диск), **1.0.49–1.0.51** (cleanup, CPU clamp, host metrics, prefer-git version).

# ARDTT v0.5.215

Клиент **0.5.215** (`versionCode` 233). Серверный стек **1.0.29** (`DEPLOY_VERSION`).

## Коротко

- Официальная расшифровка: **ARDTT** — Amnezia & Raw Dial over TURN Tunnel.
- В коде больше нет идентификатора **nonamevpn**: пакет `com.ardtt.app`, VPS `/opt/ardtt`, контейнеры `ardtt-*`, переменные `ARDTT_*`, протокол установщика `ARDTT_PROGRESS|…`.
- Смена `applicationId` — это **новое приложение** для Android: обновление поверх старого APK не встанет, нужна переустановка.
- Установщик переносит `/opt/nonamevpn` → `/opt/ardtt` и снимает контейнеры `nvpn-*`. Старые `NVPN_*` в окружении и `.env` ещё читаются.
- Каскад: Hide-IP WARP ставится на **выходном** VPS; без галочки выход идёт в WAN выхода, не в Cloudflare. После одиночных обновлений входа/выхода починены утечка DNS каскада и ключи WARP.
- Обход: быстрее failover на белом списке; Hide-IP больше не расходится с фактическим Cloudflare-egress; на малых VPS — Docker 29 snapshot и prune build-cache перед обновлением стека.
- UI: знак AR/DTT, бейджи Ubuntu (Circle of Friends) и Debian, баннер доната, QS-тайл профиля, карточки hop на «Сети», заблокированные действия профиля при поднятом VPN, терминальный хром логов деплоя; с карточки сервера убрана мигающая ping-точка.
- Режим тестирования — в общих Настройках, без PIN администратора; вкладка «Тест» в любом режиме UI.
- In-app обновления смотрят в GitHub Releases репозитория **ARDTT**; APK режутся по ABI (`arm64-v8a`, `armeabi-v7a`, `x86_64`, universal).

## Каскад и Hide-IP

- Телефон знает только входной VPS. WAN и Hide-IP WARP — на **выходе** (`GET /v1/hide-ip-prefixes` у входа через `10.10.0.1`). Вход в каскаде — passthrough, свои `/32` на `warp0` не вешает.
- Hide-IP выкл. → egress с WAN выхода (не pop Cloudflare рядом со входом). Это относится и к Direct, и к Bypass.
- После standalone-обновления одного из двух VPS: DNS каскада больше не утекает мимо hop; ключи WARP на выходе переживают обновление.
- DNS `:53` по-прежнему `ip rule` prio 100 → `main`, не через WARP. Hide-IP на лету: `ip rule` + conntrack flush, без рестарта клиентского TUN. WARP-контур — `wireproxy` + `tun2socks`.

## Обход и деплой на VPS

- Медленный Bypass-failover на белом списке (Yandex жив, Cloudflare мёртв): probe не принимает TCP `:9100` за живой Direct; Auto уходит в обход.
- Несовпадение Hide-IP и фактического Cloudflare-egress устранено вместе с переходом WARP на wireproxy/tun2socks.
- Docker 29 на малых дисках: snapshot-промахи при пересборке `bypass` больше не роняют обновление; лишние deploy-файлы с хоста убираются.
- Перед обновлением VPS из приложения сбрасывается Docker build cache, чтобы на маленьком диске сборка доходила до конца.
- Логи установки/обновления в приложении — тот же терминальный хром, что вкладка «Журналы». С листа обновления сервера нельзя случайно смахнуть в залипший overlay.

## Интерфейс

- Лаунчер, QS и тайлы: белое **AR** над оранжевым **DTT** на `#181E25`.
- Карточка сервера: знак дистрибутива (Ubuntu CoF / Debian и др.) и версия ОС в бейдже, без пустой заглушки и без мигающей ping-точки.
- Баннер «Поддержка автора» на туннеле (пока подключено) и карточка в Настройках; ссылка [Спасибо Мир](https://spasibomir.ru/pay/34807).
- Quick Settings: тайл переключения VPN-профиля (не только старт/стоп).

- Пока VPN поднят, действия профиля выглядят заблокированными, а не исчезают.

## Рекомендации

- На открытой сети, если UDP до VPS проходит, оставляйте **Авто** / прямое — так быстрее.
- На белом списке ожидайте **обход** (TURN). Один hash на устройство; мёртвый звонок — recreate в настройках или диалог на Туннеле.
- Hide-IP — это egress, не третий клиентский путь. DNS туннеля не должен идти через WARP.
- Каскад: сначала ставьте **выход**, затем **вход**. Телефон коннектится только ко входу.
