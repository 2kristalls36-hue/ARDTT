# Проверка клиента на белом списке оператора

Облачный агент Cursor **не видит** USB телефона на вашем столе. Кабель помогает только той машине, на которой реально выполняется `adb`. Ниже — что уже можно автоматизировать без телефона, что даёт USB, и как собрать снимок сессии на БС.

Белый список здесь — **сеть оператора** (Yandex `77.88.8.8` жив, Cloudflare `1.1.1.1` режется), не список приложений split-tunnel и не allowlist исходящих доменов Cursor. Классификация Auto: [ARCHITECTURE.md](ARCHITECTURE.md).

## Почему кабель сам по себе ничего не даёт облачному агенту

Этот агент работает в изолированной ВМ Cursor, не на вашем компьютере. USB-порт ноутбука в эту ВМ не прокидывается. Подключить телефон кабелем к ПК, пока агент крутится в облаке, — то же самое, что не подключать.

Кабель нужен **отладчику на той же машине**, где запущен `adb`:

| Где выполняется агент | USB к вашему ПК | Что получится |
|---|---|---|
| Облачная ВМ Cursor (этот чат) | не виден | только юнит-тесты + разбор телеметрии с VPS |
| Cursor Desktop / локальный агент на том же ПК | виден, если включена отладка по USB | `adb`, logcat, скриншот, `dumpsys` |
| [Self-Hosted worker](https://cursor.com/docs/cloud-agent/self-hosted) на том же ПК | виден так же | облачный чат, а команды идут на ваш ПК |

Сейчас у этого запуска **нет** подключённого self-hosted worker. Пока worker не запущен, кабель для облачного агента бесполезен.

## Что нельзя подменить эмулятором

Настоящая БС — DPI и фильтр оператора на LTE/SIM. В облачной ВМ нет сотового радио и нет вашей SIM.

Юнит-тесты (`NetworkProbeClassifyTest`, `NetworkRecoveryPolicyTest`, `HideIpPolicyTest`) проверяют **классификатор**: «Yandex↑ Cloudflare↓ → обход». Они не проверяют VK-дозвон, TURN, живой Path B и DPI.

Эмулятор с `iptables`, который дропает `1.1.1.1`, полезен как регрессия зонда. Это не замена выездной проверки на SIM оператора.

## Четыре слоя

### 1. Всегда: юнит-тесты зонда

```bash
cd android
./gradlew :app:testDebugUnitTest --tests com.ardtt.app.core.NetworkProbeClassifyTest
./gradlew :app:testDebugUnitTest --tests com.ardtt.app.core.NetworkRecoveryPolicyTest
./gradlew :app:testDebugUnitTest --tests com.ardtt.app.core.HideIpPolicyTest
```

Их агент может гонять в облаке без телефона.

### 2. Без кабеля: режим тестирования → VPS

Уже работает. Телефон на LTE, Wi‑Fi выкл., запись на вкладке **Тест**, сценарий, **Отправить**. Агент читает JSONL с приёмника `:9200` — [TELEMETRY.md](TELEMETRY.md).

Это основной канал, пока нет worker с `adb`: кабель не нужен, сеть телефона остаётся сотовой.

### 3. Живое управление: USB-отладка на машине с `adb`

Кабель даёт канал **управления**, не интернет телефона. Данные должны идти через SIM.

**Не включайте USB-модем / RNDIS / tethering.** Иначе телефон сидит в сети компьютера (открытый интернет), Auto на Wi‑Fi/USB берёт Direct, и это уже не проверка БС.

Нужно:

1. На телефоне: **Параметры → Для разработчиков → Отладка по USB**.
2. Кабель data (не charge-only), в диалоге «Разрешить отладку» — да.
3. Wi‑Fi выкл., мобильные данные вкл., SIM на БС.
4. `adb devices` показывает `device`, не `unauthorized`.
5. `sys.usb.config` содержит `adb` и **не** содержит `rndis`.

Дальше на этой машине:

```bash
./scripts/device-bs-dump.sh
```

Скрипт пишет каталог со сводкой, зондом TCP с телефона, `dumpsys`, logcat ARDTT и скриншотом. Каталог можно приложить к обращению или залить как телеметрию.

Если облачный агент должен сам жать кнопки: на том же ПК запустите self-hosted worker ([My Machines](https://cursor.com/docs/cloud-agent/self-hosted)), оставьте телефон в USB-отладке без модема. Тогда агент сможет ставить APK, читать logcat и снимать экран. VK WebView и системный диалог VPN по-прежнему могут потребовать один тап человеком.

Отдельное приложение по Wi‑Fi, без USB и без worker — [слой 4](#слой-4-отдельное-приложение-по-wi-fi--тест-lte). Без lab-режима в ARDTT оно сломает Auto.

### 4. Companion по Wi‑Fi + LTE (пока схема)

Отдельный процесс держит канал к агенту на Wi‑Fi, ARDTT в lab-режиме смотрит только LTE. Правила готовности сессии — юнит-тесты `LabRadioPlanTest`. Runtime (WSS на VPS, второй APK) ещё не собран. Подробности ниже.

## Как читать зонд с `adb`

Приложение биндит пробы на **underlay** (сеть без VPN). `adb shell` ходит в default route: если туннель уже поднят, `1.1.1.1` начнёт отвечать **через обход**, даже когда underlay — БС. Это как раз признак, что Path B жив, а не что «списка нет».

Поэтому два снимка:

| Фаза | Туннель | Ожидание на БС |
|---|---|---|
| `underlay` | выкл. | Yandex ok, Cloudflare fail, класс `NeedBypass` |
| `tunnel` | обход вкл. | Cloudflare/интернет ok **через VPN**; в logcat `ConnMgr` путь Bypass |

```bash
./scripts/device-bs-dump.sh --phase underlay   # туннель выключен
# Подключить в приложении, дождаться «обход»
./scripts/device-bs-dump.sh --phase tunnel
```

IP provision по умолчанию `45.129.2.3:9100`. Другой VPS: `ARDTT_VPS_HOST` / `ARDTT_VPS_PORT`.

## Чеклист сессии на БС

1. Wi‑Fi выкл., LTE вкл., USB только зарядка+adb, не модем.
2. Режим тестирования вкл., запись начата, комментарий «БС, оператор …».
3. Auto, не «только прямое».
4. Экран туннеля: preselect «обход», не «прямое».
5. Подключить. Path B, не AWG UDP.
6. Сайт, который на underlay не открывался, открывается. Hide-IP — по сценарию.
7. Снимок: `./scripts/device-bs-dump.sh --phase tunnel` и/или **Отправить** лог на VPS.

## Чего USB не заменяет

- Живую SIM и DPI оператора.
- Сессию VK / hash звонка, если её ещё нет на устройстве.
- Доступ облачной ВМ к вашему USB без self-hosted worker.

Пока worker не стоит: юнит-тесты здесь, живая БС — запись на телефоне и загрузка на `:9200`. Интерактив без USB — слой 4 (lab-режим + канал на VPS), его runtime ещё не собран.

## Слой 4: отдельное приложение по Wi‑Fi + тест LTE

Идея верная: облачному агенту нужен **свой** канал на телефон, независимый от USB и от туннеля, который мы как раз ломаем/чиним. Wi‑Fi для управления, SIM для белого списка.

Просто включить Wi‑Fi и поставить второе приложение **нельзя**. Сейчас, если AP жив:

- [pickBestUnderlayNetwork](../android/app/src/main/java/com/ardtt/app/core/UnderlayAccess.kt) ставит Wi‑Fi выше LTE;
- [autoUsesDirectOnWifi](../android/app/src/main/java/com/ardtt/app/core/ConnectPath.kt) на Auto сразу берёт Direct, зонд БС не смотрит;
- доверенный Wi‑Fi может **поставить VPN на паузу**.

Управление поедет, проверка белого списка — нет.

Нужны **две сети сразу**, каждая со своим bind:

```
облачный агент ──HTTPS──► VPS (реле :9200 / WSS)
                              ▲
                              │ исходящий сокет, bind = Wi‑Fi
                         companion / lab-агент
                              │ Intent, не default-network
                              ▼
                           ARDTT
                              │ bind underlay = LTE (lab-режим)
                              ▼
                     оператор / белый список
```

Телефон сам открывает исходящий канал на VPS. Облачная ВМ в домашнюю LAN не стучится.

### Зачем отдельный процесс

| | Агент внутри ARDTT (вкладка «Тест») | Отдельный APK (`com.ardtt.lab`) |
|---|---|---|
| Поставить | уже на телефоне | второй APK |
| `bindProcessToNetwork(Wi‑Fi)` | нельзя: сломает зонд и TURN | да: весь C2 сидит на AP |
| Когда VPN поднялся | сокеты C2 надо `protect()` или исключить пакет | пакет в `addDisallowedApplication` (режим ЧС) |
| Режим БС приложений | агент не в allow-list — C2 сам уходит в underlay | то же, не добавлять lab в список |
| Риск | один процесс, легко смешать сети | два процесса, границы ясные |

Отдельное приложение лучше по изоляции. Быстрее начать с lab-агента **внутри режима тестирования** (исходящий WSS + принудительный LTE), а во второй APK вынести, если `protect()`/split-tunnel начнут мешать.

На типичной БС TCP до IP VPS (`:9100` / `:9200`) часто жив, режется UDP и `1.1.1.1`. Тогда C2 можно держать по LTE без Wi‑Fi — это уже телеметрия, только двусторонняя. Wi‑Fi нужен, чтобы **не потерять управление**, когда туннель или LTE падают, и чтобы скрин/logcat не шли через проверяемую сеть.

Правила сессии — [LabRadioPlan.kt](../android/app/src/main/java/com/ardtt/app/core/LabRadioPlan.kt): готово только если LTE есть, канал к агенту есть (Wi‑Fi или TCP VPS), и включён lab-режим «underlay = cellular».

### Что должен уметь companion

Исходящий WebSocket/HTTPS на VPS с токеном. Команды узкие, не произвольный shell:

- статус: Wi‑Fi / LTE / VPN, класс зонда, путь, версия;
- зонд, **явно bind на cellular** `Network`;
- connect / disconnect через exported Intent ARDTT (режим тестирования);
- скрин, logcat, последние JSONL;
- держать LTE живым: `requestNetwork(TRANSPORT_CELLULAR)` — иначе OEM гасит mobile data при Wi‑Fi.

Не нужно: полный UI-робот с первого дня. Диалог VPN и VK WebView всё равно могут потребовать один тап человеком.

### Обязательный lab-режим в ARDTT

Пока этого нет в runtime, companion только мешает. Нужно (выкл. по умолчанию, только режим тестирования):

1. `preferCellular` в [scoreUnderlayCandidate](../android/app/src/main/java/com/ardtt/app/core/UnderlayAccess.kt) — уже есть, в `pickBestUnderlayNetwork` ещё не включён.
2. [labEffectiveUnderlayKind](../android/app/src/main/java/com/ardtt/app/core/LabRadioPlan.kt) вместо «сырого» Wi‑Fi в Auto / handover.
3. Пакет companion всегда в transport-исключениях TUN, рядом с VK.
4. SSID управления не считать доверенным Wi‑Fi (не паузить туннель).
5. C2-сокеты companion: `bindSocket(wifi)` или `bindProcessToNetwork(wifi)`.

### Чего Wi‑Fi-приложение не отменяет

- Живую SIM и DPI.
- OEM, который не поднимает LTE параллельно с AP — тогда только слой 2 (телеметрия, Wi‑Fi выкл.) или USB.
- Безопасность: это удалённое управление телефоном. Только тестовая сборка, токен, исходящий канал, без произвольного shell.

Порядок сборки: lab-режим в ARDTT → двусторонний канал на `:9200` в режиме тестирования → если C2 прёт в VPN, вынести во второй APK.
