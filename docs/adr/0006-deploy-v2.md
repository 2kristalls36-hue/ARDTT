# ADR 0006 — деплой v2: один образ, один скрипт, один контейнер

- Статус: принято, реализуется
- Дата: 2026-11-23
- Стек: 2.0.0

## Контекст

Деплой 1.0.x (стек до 1.0.57 включительно) устроен как цепочка из девяти звеньев:
приложение передаёт на VPS `fetch-and-install.sh` и overlay host-файлов; фетчер
разбирает индекс релиза, скачивает Docker Engine, Compose CLI и каждый слой образа
отдельным ассетом, восстанавливает кэш слоёв через `docker save`, собирает tar,
вызывает `install.sh`; тот ведёт каталоги релизов, атомарные указатели
`current`/`previous`, журнал фаз, бюджет диска, GC образов и релизов, запускает
Compose. Объём — около 6 000 строк shell/Python на сервере, Go-бинарь `ardttctl`,
около 40 скриптов сборки и проверок, около 2 200 строк Kotlin.

Выявленные недостатки:

1. **Сложность и хрупкость.** Большинство дефектов, найденных при проверке на
   VPS 23.11.2026, находились в обвязке, а не в самом VPN-стеке: подсеть менялась
   при каждом обновлении из-за ошибки чтения меток сети; кэш слоёв, частичные
   пакеты и overlay требуют согласованности трёх источников версий.
2. **Скорость и объём.** Compose CLI (62 МБ) и Engine (~70 МБ) скачиваются на
   VPS, порог свободного места — 1,6 ГБ даже при повторном деплое.
3. **Вмешательство в хост.** Собственный `docker.service` и `ardtt-containerd`
   подменяют системный Docker; iptables доустанавливается отдельной веткой кода.
4. **Наблюдаемость в приложении.** Ошибки возникают в звеньях, которых
   пользователь не видит (индекс, overlay, кэш), и формулируются в их терминах.

## Решение

### Артефакты релиза

Для версии стека `X` и архитектуры `A ∈ {amd64, arm64}` в GitHub Release
приложения публикуются:

| Ассет | Содержимое |
|-------|-----------|
| `ardtt-server-X-linux-A.image.tar.gz` | `docker save ardtt/server:X` + gzip |
| `ardtt-deploy.sh` | установщик (тот же файл, что в APK) |
| `SHA256SUMS-server.txt` | суммы серверных ассетов релиза |

Индекс, послойные ассеты, overlay host-файлов, Engine, Compose CLI и `ardttctl`
не публикуются. Источник образа — только GitHub Release (решение владельца
продукта 23.11.2026); реестры (GHCR, Docker Hub) не используются.

### Установщик

Один POSIX-совместимый bash-скрипт `server/deploy/ardtt-deploy.sh` без
зависимостей, кроме `docker`, `curl` или `wget`, `sha256sum`, `flock`, `ss`.
python3 не требуется. Приложение передаёт его по SFTP при каждом запуске, поэтому
версия установщика всегда совпадает с APK.

Действия (`ARDTT_ACTION`): `install` (включает обновление и миграцию),
`uninstall`, `status`.

Порядок `install`:

1. Проверки: root, архитектура, `/dev/net/tun`, свободная память.
2. Docker. Если `docker info` проходит — используется как есть, не обновляется и
   не перезапускается. Если Docker отсутствует — ставится из репозитория
   дистрибутива (`apt-get install docker.io`, `dnf install moby-engine`,
   `apk add docker`, `zypper install docker`) с подавлением `needrestart`.
   На RHEL/Alma/Rocky пакета нет: установщик завершается с `DOCKER_MISSING` и
   командой ручной установки. Если CLI есть, а демон не отвечает — отказ
   `DOCKER_NOT_RUNNING` (чужой Engine не трогаем).
3. Образ. Если образ `ardtt/server:X` уже загружен — шаг пропускается. Иначе:
   проверка места (`5 × размер файла + 300 МБ`), загрузка файла образа во
   временный каталог `/opt/ardtt/tmp`, сверка SHA-256 (из `ARDTT_IMAGE_SHA256`
   либо `SHA256SUMS-server.txt` того же релиза), `docker load`, удаление файла.
4. Параметры экземпляра: идентификатор, порты, подсеть, роль, каскад. Берутся из
   `/opt/ardtt/instance.env` (v2) или из `instance.json`/`.env` установки 1.0.x;
   при первой установке — из переменных окружения. Занятый порт при
   `ARDTT_AUTO_PORTS=1` заменяется следующим свободным; порты, которые держит
   собственный контейнер ARDTT, занятыми не считаются.
5. Сеть `ardtt-<id>` с метками `com.ardtt.owner=ardtt`,
   `com.ardtt.instance=<id>` и подобранной подсетью; существующая собственная
   сеть переиспользуется.
6. Секреты (`admin.token`, `telemetry.token`, `cascade.secret`) — файлы 0600 в
   `/opt/ardtt/data`; ключи каскада генерируются образом (`awg genkey`).
7. Переключение:
   - работающий контейнер ARDTT останавливается (`docker stop -t 30`) и
     переименовывается в `ardtt-prev`;
   - новый контейнер создаётся `docker run` с теми же ограничениями, что
     в Compose 1.0.x (`cap_drop ALL` + `NET_ADMIN`, `NET_RAW`, `SETUID`,
     `SETGID`; `no-new-privileges`; лимиты памяти, CPU, PID; журнал 3 × 10 МБ);
   - проверка готовности (`ready.sh` в контейнере, до 120 с);
   - успех: `ardtt-prev` удаляется; образы ARDTT, кроме текущего и
     предыдущего, удаляются;
   - неуспех: новый контейнер удаляется, `ardtt-prev` переименовывается обратно
     и запускается; ошибка `READINESS_FAILED` с выдержкой из журнала контейнера.
8. Запись `instance.env`, вывод `ARDTT_DONE`.

Compose не используется: для одного контейнера он не даёт ничего, кроме
зависимости в 62 МБ.

Provision публикуется на `0.0.0.0` по умолчанию, telemetry — на `127.0.0.1`.
Это пересматривает умолчание ADR 0005: приложение и клиентские устройства
обращаются к provision по публичному адресу сервера, SSH-туннеля в приложении
нет, поэтому при публикации только на `127.0.0.1` управление сервером и
клиентские функции (профиль, присутствие, Hide IP) не работают. Защита
эндпоинтов токенами и TLS (ADR 0005) сохраняется.

### Миграция с 1.0.x

Выполняется автоматически внутри `install`, если найдена установка 1.0.x
(`/opt/ardtt/instance.json` или контейнер с меткой `com.ardtt.owner=ardtt`):

- идентификатор экземпляра, порты, подсеть, роль, параметры каскада и публикация
  provision переносятся; каталог `data` остаётся на месте (тот же путь);
- контейнер 1.0.x проходит шаг 7 как предыдущая версия, то есть при неуспехе
  возвращается;
- после успешной проверки готовности удаляются только артефакты 1.0.x внутри
  `/opt/ardtt`: `releases/`, `current`, `previous`, `staging/`, `incoming/`,
  `cache/`, `state/`, `bin/docker-compose`, `install-lib/`, `.env`,
  `instance.json`, `*.lock`;
- собственный Docker Engine 1.0.x (`docker.service` с описанием «ARDTT bundled
  Docker Engine») **не удаляется**: на нём могут работать чужие контейнеры.

### Протокол вывода

Сохраняется строковый протокол, который приложение уже разбирает:
`ARDTT_PROGRESS|доля|шаг`, `ARDTT_INFO|…`, `ARDTT_WARN|…`,
`ARDTT_ERROR|code=КОД|сообщение`, `ARDTT_CASCADE_PUBLIC_KEY|ключ`,
`ARDTT_DONE|k=v|…`. Состав полей `ARDTT_DONE` не меняется. JSON-протокол 2 и
`ardttctl` упраздняются.

Коды ошибок: `NOT_ROOT`, `UNSUPPORTED_ARCH`, `TUN_MISSING`, `LOW_MEMORY`,
`DOCKER_MISSING`, `DOCKER_INSTALL_FAILED`, `DOCKER_NOT_RUNNING`,
`INSUFFICIENT_DISK`, `DOWNLOAD_FAILED`, `SHA256_MISMATCH`, `IMAGE_LOAD_FAILED`,
`PORT_BUSY`, `SUBNET_EXHAUSTED`, `CONTAINER_START_FAILED`, `READINESS_FAILED`,
`ROLLBACK_FAILED`, `DEPLOY_IN_PROGRESS`, `FOREIGN_CONTAINER`.

### Изоляция от соседей

Установщик изменяет на хосте только:

- `/opt/ardtt`;
- объекты Docker с меткой `com.ardtt.instance=<id>` (контейнеры, сеть) и образы
  `ardtt/server:*`;
- при отсутствии Docker — пакеты Docker из репозитория дистрибутива.

Не выполняются: `docker system prune`, `docker compose down` чужих проектов,
изменение `/etc/docker/daemon.json`, sysctl хоста, правила iptables вне цепочек
Docker. Проверяется VPS-лабораторией (`.github/workflows/vps-lab.yml`) до
публикации релиза.

### Удаление

`ARDTT_ACTION=uninstall`: контейнеры и сеть экземпляра, образы `ardtt/server:*`,
каталог `/opt/ardtt` (данные — только при `ARDTT_PURGE_DATA=1`). Docker остаётся.

## Последствия

- Код установщика сокращается примерно с 6 000 до 600 строк; упраздняются
  `fetch-and-install.sh`, `install.sh`, `install-lib/`, `ardttctl`, сборка
  индекса и слоёв, overlay host-файлов.
- Каждое обновление скачивает образ целиком (около 50 МБ в gzip). Это меньше,
  чем Compose CLI, который скачивал 1.0.x при первой установке.
- APK 0.5.x с установщиком 1.0.x не находят в новых релизах ассетов старого
  формата. Перед деплоем стека 2.x приложение должно быть обновлено; переход
  обозначается сменой мажорной версии стека.
- Пользователи RHEL/Alma/Rocky ставят Docker вручную (одна команда в тексте
  ошибки).
